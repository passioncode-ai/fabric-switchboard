# M4: release and update

## Map

1. **Release PR and tag, by hand.** `scripts/release_bump.py` moves the version in the plugin, marketplace, skill, Cargo, npm and Tauri files and opens `## X.Y.Z` in the CHANGELOG; the PR merges; a person or agent pushes `vX.Y.Z` on the merge commit. Nothing automates the tag, the watch, a rerun or the local install.
2. **`release.yml` on the tag.** `preflight` checks the tag against the declared versions and the CHANGELOG section. `guard` (org `release-guard@v1`) requires main to contain the commit and the newest `nightly.yml` run on that SHA to be `success`; with none it dispatches one once and waits 60 minutes. `macos`, `windows` x2 and `linux` x2 build and sign (Windows and Linux re-run the native tests; Linux runs `apt-get` without retries). `updater` writes `latest.json` (an `Urgent:` CHANGELOG line adds `urgent`; nothing can add `needs_migration`). `publish` (org workflow) refuses a tag not newer than latest, drafts, uploads, publishes; concurrency per tag.
3. **Feed.** Every copy reads `releases/latest/download/latest.json`.
4. **App** (macOS, Windows, AppImage): check 90 s after start then every 5 minutes, download, minisign and signed-version check; macOS swaps the bundle at once, Windows runs NSIS at quit; restart at an idle moment at most once in 6 hours unless urgent; after 30 minutes held only by requests in flight, answer new ones 503 and drain 90 s; a window that does not own the data folder installs nothing (DEC-0026).
5. **`serve`.** Same 5-minute check; installs when it may write the app (`access(2)`); when its program was replaced it waits for two quiet looks (at most 30 minutes), drains 8 s and exits 75 for its supervisor; unsupervised it logs once and stays on the old program. A `.deb` only prints commands that need `sudo`; a CLI tarball does nothing.
6. **What outlives an update.** `switchboard mcp` sends each call to a fresh copy of the new program (SB-375); session hosts and dispatched runs survive on macOS (own sessions and process groups); under systemd they sit in `serve`'s cgroup.
7. **Across machines.** No command updates another machine. The Studio spaces depend on studio-agent running `switchboard update` as the owning account on a schedule plus each space's `serve` restarting under launchd. Remote reads (`remote-status`, `ssh-serve`, `accounts lease`) fall back for an older Switchboard; nothing compares versions.
8. **Plugin channel.** `claude plugin marketplace add passioncode-ai/fabric-switchboard` serves `plugins/switchboard` from main HEAD; `autoUpdate` unset; this Mac had plugin 0.7.117 while the CLI was 0.7.122.

Live state at the read: v0.7.122 Latest (13:23Z); the v0.7.123 run started 13:24Z; v0.7.118's run failed and has no release; v0.7.121 took about 1.5 h tag to publish.
