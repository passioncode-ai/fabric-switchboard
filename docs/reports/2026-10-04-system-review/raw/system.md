## Internet research by block

Developer issues/forums are leads and ecosystem observations; they do not prove a defect in our product. Technical decisions below rely on specification/SDK/vendor sources and local code. No external thread is taken as permission to change auth or replay work.

1. **Token custody and vault.** [OAuth security BCP RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14) explains replay detection and rotating refresh-token lineage: copied refresh state needs one serialized spender and successor preservation. [Claude Code concurrency issue #80585](https://github.com/anthropics/claude-code/issues/80585) and [Codex race #10332](https://github.com/openai/codex/issues/10332) describe independent clients racing refresh. This supports our access-only isolated homes, owner mutation lock, active-account hold, provider-owner attribution and successor stash. It does not prove that every upstream version uses identical lock/cache semantics. [Codex keyring issue #22453](https://github.com/openai/codex/issues/22453) supports treating repeated vault access as a UX/resource concern; the relevant lifecycle fix is already landed. [Microsoft CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) confirms user-context protection; machine-wide protection has different access semantics. Our `CRYPTPROTECT_UI_FORBIDDEN` and absence of `CRYPTPROTECT_LOCAL_MACHINE` are appropriate. Windows user-separation must still be checked on a real host.

2. **Backups/recovery.** [Bitwarden encrypted exports](https://bitwarden.com/en-gb/help/export-your-data/) distinguishes key/account restricted files from password protected portable export; losing or rotating the key changes recoverability. [Developer/user discussion on the restricted default](https://community.bitwarden.com/t/make-password-protected-the-default-predefined-choice-for-encrypted-json-exports/83905) illustrates why naming an encrypted file a disaster-recovery backup can mislead people. Our machine-key backup is a deliberate D-5 choice, not cross-device recovery. Keep its clear explanation and defer portable export as its own product/security design. The collision defect below is independent of that decision.

3. **MCP/CLI.** [Official MCP stdio guidance](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/stdio.md) requires protocol-only stdout and lifecycle cleanup at EOF. [SDK issue #2776](https://github.com/modelcontextprotocol/typescript-sdk/issues/2776) shows that unconsumed piped stderr can hang transport; avoid verbose server diagnostics and test the real client launcher. [Official protocol version guide](https://ts.sdk.modelcontextprotocol.io/v2/protocol-versions) and [2026-07-28 specification source](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/index.mdx) introduce per-request metadata/stateless lifecycle. Our legacy server may interoperate via client fallback; do not just add 2026-07-28 to `VERSIONS`, because that would advertise unimplemented semantics. Actual compatibility depends on the client. Current root scope does not need a wholesale SDK rewrite.

4. **Lifecycle/residency.** [Tauri system tray](https://v2.tauri.app/learn/system-tray/) provides tray creation/show/focus and explicit Quit; [maintainer-community discussion #2684](https://github.com/orgs/tauri-apps/discussions/2684) highlights platform differences between closing a window, hiding it, and exiting. [Tauri issue #9198](https://github.com/tauri-apps/tauri/issues/9198) records exit-handler surprises. A background account manager should have one explicit residency preference and visible owner state, while Quit must retain the existing bounded drain. Do not silently change closing a window to continued account mutation: SB-28 is an operator decision. Landed 0.5.4 drain/stable proxy/idle budget already answers the engineering half.

5. **Windows distribution.** [Tauri NSIS sidecar issue #15134](https://github.com/tauri-apps/tauri/issues/15134) records stale cached sidecars on same-version reinstall. It is a design warning for SB-05, not evidence that our current installer has that issue (it deliberately does not embed the CLI). [Tauri Windows installer guidance](https://v2.tauri.app/distribute/windows-installer/) and the repository's CI-built receipt own distribution behavior. Adding the CLI needs exact artifact-byte verification through install/upgrade/reinstall and PATH refresh; no incidental process kill from a suggested forum hook. Azure Authenticode and the generated uninstaller are separately open, not green because NSIS built.

6. **CI/release.** [GitHub schedule documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) says scheduled execution can be delayed and only runs on the default branch; [developer discussion of schedule latency](https://www.reddit.com/r/github/comments/1wtqo56/github_actions_scheduled_workflows_delayed_by/) provides corroborating experience.
