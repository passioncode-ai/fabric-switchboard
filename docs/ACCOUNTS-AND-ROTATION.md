# Account capture, native activation and quota rotation — 0.3, revised in 0.5 and 0.5.1

This is the implementation contract for the operator's additional account flow. [Plan and packet ownership](PLAN-0.3.md), [source research](RESEARCH-0.3-IMPORTS.md), [runtime](../crates/switchboard-runtime/src/lib.rs), [external adapters](../crates/switchboard-runtime/src/external.rs), [policy](../crates/switchboard-core/src/rotation.rs) and [monitor](../crates/switchboard-runtime/src/monitor.rs) are the corresponding receipts. Live provider acceptance is separate from fixture coverage.

## Three ways to add a profile

1. **Add the current CLI account** (desktop: one click on *Add to Switchboard* under *In use now*, default pool, email as label; 0.5) reads the authorization that Claude Code or Codex already stores locally. It does not start OAuth or log out. Label defaults to the source email when available; provider and pool remain explicit. Config and credentials are read twice to refuse a changing source. The app reports missing, unavailable and available separately. CLI: `switchboard accounts capture --provider claude` or `--provider codex`.
2. **Sign in to another account** (desktop: *+ Add account → Sign in to another Claude/Codex account*, no form; 0.5) opens a console running the installed official `claude auth login` or `codex login` in a fresh app-owned home. The user completes the provider's account selection. Finish captures that home, saves the profile, then cleans the staging home. The desktop polls `LoginStatus` (`pending` / `complete` / `ended`, no credential) every 1.5 s and finishes on its own; an empty label becomes the captured email (`login_state_reads_completion_and_an_exited_terminal`). *Sign in again* on a row reuses that row's label and pool, so the same identity updates in place. The ordinary account remains available; no global logout is needed. CLI: `switchboard login begin --provider claude --label Work`, followed by `switchboard login finish LOGIN_ID`.
3. **Import Claude Swap profiles** (desktop: one click, default pool; 0.5) reads `~/.claude-swap-backup` without executing Claude Swap or modifying its data. The sequence index names per-slot credential and config backups; the base64 `.enc` file takes precedence over a legacy macOS Keychain backup. Each invalid account counts as a failed import without revealing its content. Successful profiles go into Switchboard's protected vault. CLI: `switchboard accounts import-claude-swap`.

Reimport identifies an account by provider, pool and source account/organization identity. Email is a label, not the unique key. If identity is absent, exact token equality is the bounded fallback. The same known identity updates its saved generation; disabled remains disabled. A changed generation invalidates prior quota. Imported identity is a source claim, not proof that the provider accepted a request. Store `upsert` tests cover these boundaries.

## Which account is active

The **current CLI account** is observed from native authorization, independent of Switchboard's route. The renderer receives identity metadata and a matched local account ID, never token material. The signed-in identity is matched in every pool: `account_id` is the oldest matching profile and `account_ids` lists all of them, oldest first (`current_account_matches_across_pools`). A logged-in account can be visible before it is captured. Current observations are cached for at most 30 seconds, and below that the sign-in itself is read only when its source changed (0.5.4, [KEYCHAIN](KEYCHAIN.md)); capture, import and activation invalidate the cache, and an observation that overlapped an invalidation is not cached. Reading current accounts does not wait for account mutations, usage checks or the monitor (`current_accounts_do_not_wait_behind_a_mutation`). UI periodic refresh is separate from provider quota polling. `switchboard current` reads the actual CLI source.

The **selected managed account** is the route used for the next local-proxy request. An existing stream retains its captured credential. Multiple provider/pool routes can coexist. `accounts select` changes this route; it does not claim to change every console on the machine.

**Switch** (0.5: the row's primary action, one click, no confirmation; CLI `accounts activate`) explicitly activates a saved Claude OAuth profile in the ordinary CLI store. Since 0.5.1 ([PLAN-0.5](PLAN-0.5.md) §0.5.1, [comparison report](reports/2026-10-03-claude-swap-comparison/README.md)) the order is:

1. A renewed token Switchboard could not store yet is adopted first; if it still cannot be, the switch is refused (*Switchboard has not stored this account's renewed sign-in yet*). The account already in use is a no-op. Switching away from a signed-in account that is not saved in Switchboard is refused, since its newest token would be lost (`switching_away_from_an_unsaved_account_is_refused_and_the_account_in_use_is_a_no_op`). A live token whose lineage belongs to another account is refused with *The Claude Code sign-in does not match the account named in its settings* (`a_foreign_lineage_under_this_name_is_never_filed_or_switched_from`); one nothing attributes — no stored copy holds it and the provider could not be asked — is refused with *Switchboard could not confirm which account Claude Code is signed in to* (`a_live_generation_nobody_can_attribute_is_never_filed`). Two identities without an account id are never the same account (`identities_without_an_account_id_are_never_the_same_account`).
2. Claude Code's lock directories are taken in its order (`.oauth_refresh.lock`, `~/.claude.lock`, `~/.claude.json.lock`). A held lock is waited for up to 9 s; a lock older than 60 s (10 s for the config lock) is taken over, as Claude Code itself does (`a_live_lock_is_waited_for_and_a_stale_one_is_taken_over`). An existing lock directory that stays held reports that Claude is updating its account; any other failure points at the config directory's permissions (`unwritable_lock_directory_is_not_reported_as_claude_updating`). Native operations are refused when `CLAUDE_CONFIG_DIR` points into Switchboard's own data folder.
3. Under those locks, before anything is written, the outgoing live credential is re-read and stored into **every** saved copy of that identity, in every pool (`the_outgoing_generation_is_preserved_under_the_lock_before_any_write`, `switching_away_keeps_the_live_generation_in_every_pool`); the identity and lineage are checked again there. A copy that already holds a newer generation than Claude Code's item — a renewal Switchboard stored while writing it back failed — is left as it is (`a_copy_newer_than_claude_codes_item_is_not_overwritten_on_switch`). A failure here aborts the switch with nothing changed.
4. The new credential item starts from the **live** one: `mcpOAuth`, `mcpOAuthClientConfig`, `mcpXaaIdp`, `mcpXaaIdpConfig` and `pluginSecrets` stay as they are, only the account-bound keys (`claudeAiOauth`, `trustedDeviceToken`) come from the target (`shared_keys_come_from_the_live_item_and_account_keys_from_the_target`). A captured expiry never outlives its access token (`a_captured_expiry_never_outlives_its_access_token`). In `~/.claude.json` only `oauthAccount` is replaced and a managed `primaryApiKey` is removed; other settings are preserved, and a config the switch creates from nothing carries `hasCompletedOnboarding: true` so Claude Code does not start its first-run flow (0.5.2, `a_config_created_by_a_switch_skips_onboarding_and_an_existing_one_is_kept`) (`a_managed_api_key_is_removed_and_returns_on_rollback`). On macOS an existing plaintext `.credentials.json` is rewritten too, never created (`a_plaintext_copy_on_macos_is_rewritten_only_when_it_exists`).
5. A credential or config write that fails, including one that fails after committing, restores the prior state (`a_credential_write_that_fails_after_committing_is_rolled_back`); a failed rollback reports a sanitized failure. Nothing is rolled back after a lock was lost.

A live sign-in Claude Code wiped after `invalid_grant` counts as signed out and does not block a switch (`a_wiped_live_sign_in_is_signed_out_and_does_not_block_a_switch`); activation also works after `claude logout`, and an unreadable source still refuses (`activation_after_claude_logout_proceeds_and_is_journaled`). A target whose access token expired is renewed first (it is inactive by definition); when that fails, activation still proceeds while a refresh token exists, because Claude Code renews from it (`an_account_with_an_expired_access_token_still_activates`). The Keychain item `Claude Code-credentials` is written and deleted only through `/usr/bin/security` — the executable Claude Code itself uses — with the value on stdin as hex (argv only above the 4 KB `security -i` line buffer, Claude Code's own fallback), so neither Switchboard nor Claude Code meets a consent dialog afterwards ([PLAN-0.5](PLAN-0.5.md) C-2). Every attempt on a saved profile records `activation completed` or `activation failed`. No process is killed and no prompt is replayed. A running client may cache its token; the exact adoption delay requires live version-specific acceptance. Codex native takeover is not implemented; its capture, isolated login/launch and managed routing are available.

## Usage lifecycle

While the desktop or `switchboard serve` owns the store, a scheduler considers due enabled OAuth accounts every 30 seconds (0.5.4; 10 s before), probes at most four per pass, and normally schedules each successful observation 180 seconds later. It uses fixed provider quota endpoints, not inference requests. Oldest due goes first. Larger collections can wait longer than 180 seconds; actual timestamps are authoritative.

Claude observations preserve five-hour and seven-day limits and supported model windows. Codex preserves primary and secondary windows. The aggregate is the highest reported utilization. Inference response headers report only the five-hour and seven-day windows; they update those windows inside the stored observation of the same credential generation and keep the others (for example `seven_day_opus`), dropping a kept window whose reset has passed. The aggregate is recomputed and `observed_at` moves to the header time (`header_usage_merges_into_stored_windows_and_is_not_journaled`). Each window retains its reset time when provided. Missing, malformed, nonfinite or out-of-range observations do not become zero. A failed probe preserves the last valid result and records failed health; repeated failures back off up to 1800 seconds. A probe the provider answers with 429 waits as asked (0.5.1): a numeric `Retry-After`, at most six hours, else 900 seconds, never sooner than the ordinary backoff; the row reads *Usage checks are rate limited by the provider* (`a_rate_limited_usage_check_waits_as_the_provider_asks`, `usage_checks_report_the_providers_wait_and_never_its_body`). API keys and setup tokens do not imply subscription quota. See proxy parser fixtures and monitor backoff tests. New observations and health records more than 60 seconds ahead of the system clock are refused; already stored times are not re-checked against the clock, so setting the clock back never blocks opening the store or later writes. A newer write supersedes such a future-stamped record, and the monitor treats its schedule as due (`clock_set_back_after_observation_keeps_store_open_and_writable`, `schedule_written_before_the_clock_moved_back_is_due_now`).

The ordinary provider CLI owns the refresh of **its** account. Every 180 seconds, the monitor can adopt a newer current credential generation for an identity already captured in Switchboard. It never silently adds a new identity or enables a disabled profile.

**Inactive Claude accounts are refreshed by Switchboard (0.5, [PLAN-0.5](PLAN-0.5.md) D-2), as Claude Swap does.** Before a quota check, an inactive Claude OAuth account whose access token expires within 600 seconds is renewed with a refresh grant (`POST https://platform.claude.com/v1/oauth/token`, Claude Code's public client id, 10-second timeout, no redirects); a check the provider answers with 401 is retried once after a forced renewal ([refresh](../crates/switchboard-runtime/src/refresh.rs), [monitor](../crates/switchboard-runtime/src/monitor.rs) `check`). The new generation goes to every stored copy of the same lineage in every pool (`an_inactive_expired_account_is_refreshed_in_every_pool`). It never runs for the identity signed in to the ordinary Claude Code, nor when that sign-in cannot be read (`the_ordinary_claude_code_account_is_never_refreshed`). It runs under the owner's mutation lock, so an activation cannot hand Claude Code a refresh token mid-grant. `invalid_grant` is permanent: the row shows *Sign in again* until a new capture or sign-in replaces the credential (`invalid_grant_requires_sign_in_until_the_credential_is_replaced`, `MonitorStatus.sign_in_required`); the rejected lineage is remembered across restarts as a fingerprint in `renewal-state.json`, never the token (`a_rejected_lineage_is_remembered_across_restarts`). **A grant never loses its successor (0.5.1).** The grant runs in its own task and keeps the successor, keyed by the token it spent, before anything else happens — a caller that gives up at its deadline, a dropped control request or a cancelled check cannot drop it (`a_grant_whose_caller_gives_up_still_keeps_the_successor`). It then goes to every copy still holding the spent token, and is forgotten only once they have it. When the token endpoint names the account it issued the token to, only that account's copies get it; a copy of another account holding the same token is a dead lineage there (`a_renewal_issued_to_another_saved_account_reaches_that_account`, `a_token_issued_for_another_account_is_a_dead_lineage_here`; store side `a_renewal_goes_only_to_the_owner_the_token_endpoint_named`). A successor the vault refuses stays kept and is adopted before the next grant or switch (`a_renewed_token_that_cannot_be_stored_is_kept_and_adopted_later`). Kept successors live in memory: a successor is kept only while the vault refuses to store it (Keychain locked or denied, disk full), and it is stored on the next pass; quitting while the vault still refuses loses it, and the row then reads *Sign in again*. Writing it anywhere else would mean a plaintext copy, which Switchboard never makes. Other failures back off 60 s doubling to 1800 s and keep the stored token (`transient_failures_back_off_and_keep_the_token`). `invalid_client` is no account's fault — the provider refused Claude Code's client id itself — so it holds every renewal for an hour without a dead lineage or a per-account backoff, then one grant tests the client again; meanwhile `MonitorStatus.renewal_blocked` is true and the Automatic switching bar says renewals are refused (0.5.2; `a_refused_client_holds_every_renewal_without_blaming_an_account`, `a_refused_client_after_the_hold_is_tried_once_more`). Codex accounts are not refreshed (board SB-13).

**Lineage of the live sign-in (0.5.1).** The monitor copies Claude Code's newer generation of an account into Switchboard only when the live refresh token is that account's own: it matches a stored copy of the same identity, or `GET /api/oauth/profile` (asked once per unknown lineage, outside every lock) names that account. The provider is asked before each native rotation too, and an unanswered question waits a minute (`an_unanswered_owner_question_waits_a_minute`). A token that belongs to another stored account, that the provider attributes to someone else — the same login in another organization counts as someone else — or that nothing attributes yet, is never filed under the name in `~/.claude.json` (`background_sync_never_files_another_accounts_lineage`, `the_provider_names_the_owner_of_an_unknown_live_lineage`, `the_same_login_in_another_organization_is_another_account`).

**The account in use is left to Claude Code until it is idle (0.5.1).** When Claude Code has left its own access token expired for more than 300 seconds and the lineage is its own, Switchboard renews it under Claude Code's two credential locks — not the config lock, so Claude Code can keep writing `~/.claude.json` meanwhile (`a_renewal_takes_only_the_credential_locks`) — writes the result back into the live item with every other key intact, into an existing macOS plaintext copy (`a_renewed_live_item_reaches_an_existing_plaintext_copy_only`), and into every saved copy (`an_idle_live_account_is_renewed_in_claude_code_and_every_copy`, `a_renewed_live_item_keeps_every_other_key`). An item that changed between the read and the locks is left alone (`an_idle_live_item_that_changed_is_left_alone`). A write that fails keeps the successor, and the next pass writes it to Claude Code before anything else, without a second grant (`an_idle_renewal_that_cannot_be_written_is_stashed`). A successor the token endpoint issues to another account still goes back to Claude Code, so it stays signed in, and is remembered as foreign rather than filed; the configured account's copies, holding the spent token, then read *Sign in again* (`an_idle_renewal_issued_to_another_account_stays_with_claude_code_only`).

**Isolated launches want hours (0.5.1).** Isolated sessions receive the access token only, so they hold no refresh lineage Switchboard could rotate away. A launch renews an inactive account first when less than four hours of token life remain; for the account Claude Code is signed in to, the live (newest) token is used instead (`an_isolated_launch_wants_hours_of_token_life`).

**Claude Swap beside Switchboard (0.5.1, revised in 0.5.3).** Two renewers of one lineage spend each other's refresh token, and two automatic switchers undo each other's choice, so Switchboard divides the work by what Claude Swap is doing:

- *Running* — any `cswap` / `claude_swap` process, the menu bar (`cswap menubar`) included; a leftover LaunchAgent plist alone proves nothing (`only_claude_swap_itself_counts_as_running`, `claude_swap_switching_is_told_from_merely_running`). Switchboard does not renew the identities Claude Swap holds and takes Claude Swap's newer generation of each into every stored copy (`a_running_claude_swap_renews_its_accounts_and_switchboard_follows_it`). A row Swap is rewriting this pass keeps its account held — it is the account Swap is renewing — matched by the row's email, so a row broken for good or an account removed from Swap holds nothing (`a_claude_swap_row_that_could_not_be_read_stays_held`, `only_the_unreadable_rows_account_stays_held`). `MonitorStatus.claude_swap_accounts` counts them.
- *Switching* — `cswap auto` runs, or the menu bar runs with its own automatic switching on (`menubar_settings.json` `auto_switch_enabled`). Native rotation holds with `claude_swap_switching` and says so; manual switches and managed routes are unaffected (`native_rotation_leaves_switching_to_an_auto_switching_claude_swap`, `MonitorStatus.claude_swap_switching`).
- *Stopped* — its files still hold whatever it renewed last. They are read every pass while it runs, once when Switchboard starts, once after Swap stops, and whenever their signature (count, size, newest change) moves; a failed read is repeated (`claude_swaps_files_are_read_when_they_can_hold_something_new`, `claude_swaps_files_change_their_signature`). Newer generations are taken by the same rule and nothing is held (`a_stopped_claude_swap_still_hands_over_what_it_renewed_last`); a copy marked *Sign in again* comes back when Swap holds its successor (`a_dead_copy_comes_back_when_claude_swap_holds_its_successor`) — board SB-21.

Switching Claude Code to an account Claude Swap holds first reads Swap's profile for it and takes a newer generation, so Claude Code never receives a token Swap already spent; while that account's own row cannot be read the switch is refused with *Claude Swap is updating this account. Retry in a moment.*, an account Swap no longer lists is released, and after Swap stopped the switch takes its last generation and holds nothing (`switching_to_an_account_claude_swap_renews_takes_its_newest_generation_first`, `switching_to_an_account_swap_no_longer_lists_is_not_refused`, `a_switch_after_claude_swap_stopped_takes_its_generation_and_holds_nothing`). Whether the account is in use right now — before a renewal and before every switch — is always read afresh, never from the background's 30-second reuse. The import result carries `claude_swap_running`. Import prefers a Claude Swap session profile's credential when it expires later than the backup and the session's own config still names the slot's account (`a_newer_session_profile_generation_wins_over_the_backup`).

**Nothing moves backwards (0.5.3).** A generation is ordered by its refresh token and expiry; every writer keeps the newest:

- Re-importing from Claude Swap keeps a newer generation Switchboard holds for that identity, starts a new copy in another pool from it, and skips another account's lineage (`importing_from_claude_swap_never_moves_an_account_backwards`).
- Restoring a backup starts a restored copy from the newest generation saved in any pool (`a_restored_copy_starts_from_the_newest_generation_saved_elsewhere`).
- The background copy of Claude Code's own generation never replaces a copy newer than Claude Code's item (`background_sync_never_moves_a_newer_copy_back`), nor does a switch's preserve step (`a_copy_newer_than_claude_codes_item_is_not_overwritten_on_switch`).
- Capturing the current sign-in refuses another account's lineage, and an unattributed one when a saved copy would be overwritten; a first capture of a new account works offline (`capturing_another_accounts_lineage_under_this_name_is_refused`, `capturing_an_unattributed_sign_in_never_overwrites_a_saved_copy`).
- A successor the token endpoint issues to a saved account reaches that account even when its copies hold an older lineage of its own (`a_successor_issued_to_a_saved_account_with_an_older_lineage_still_reaches_it`).

**One renewer per lineage (0.5.3).** A refresh token is marked in flight from just before its grant until the grant task ends, however it ends; no second grant spends it, and switching to that account is refused meanwhile with *Switchboard is renewing this account's sign-in. Retry in a moment.* (`an_account_whose_renewal_is_in_flight_is_not_switched_to`). Only the owner of the real data folder renews: the offline CLI and MCP server never make a grant — they cannot see Claude Swap's holds or the owner's state — and still refuse lineages from the owner's journal (`the_offline_cli_never_spends_a_refresh_token`, `the_offline_cli_still_refuses_a_lineage_the_owner_saw_rejected`); a `serve --data-dir` owner never renews either. Rotation never picks a rejected sign-in as a candidate, so the next eligible account is tried (`rotation_skips_a_rejected_sign_in_for_the_next_eligible_account`).

## Automatic switching

Policies persist per provider, pool and target. Only one native Claude policy can be enabled across pools within this store, because the ordinary CLI account is one shared target. Default is off. Targets are `managed` (Claude/Codex next-request route) and `claude_cli` (ordinary Claude OAuth). The initial UI/CLI settings are 90% threshold, 10 percentage points hysteresis, 1800-second cooldown and maximum observation age 300 seconds. The user can change them within backend bounds.

A policy must know the current account and have usable recent quota. At threshold, candidates stay within the same provider/pool, must be enabled with usable credentials — unexpired for `managed`; for `claude_cli` an expired access token with a refresh token is enough, since Claude Code renews it (`native_rotation_switches_to_an_expired_but_renewable_account`) — and fresh successful quota, and must have sufficient headroom below threshold. The deterministic policy chooses a candidate; a native switch additionally rechecks the current identity so an external manual login cannot be overwritten using an earlier decision. A manual selection starts the cooldown. Turning off the policy stops further automatic movement; it does not undo an already completed selection.

**Limit errors (0.5, [PLAN-0.5](PLAN-0.5.md) D-6).** A seat's individual or monthly spend limit, or a per-account rate limit, answers 429 while the quota endpoint still shows capacity. Switchboard holds an account as *limited* when (a) managed requests through its proxy were refused with 429 twice within five minutes (`request rate_limited` in the journal, last 15 minutes; a single 429 is a burst, not a limit), or (b) a session transcript of the ordinary Claude Code (`$CLAUDE_CONFIG_DIR` or `~/.claude`, `projects/*/*.jsonl` changed within 15 minutes, last 256 KiB of each, at most 64 files) carries an API-error marker — `"isApiErrorMessage":true` with `"error":"rate_limit"` or status 429 — written while that account was the one in use. Head lines deserialize timestamp metadata only, skipping unknown conversation values without materializing them; tail lines deserialize only byte-filtered API-error markers, and no content is stored or logged ([limits](../crates/switchboard-runtime/src/limits.rs)). The hold lasts until the marker's `quotaLimits.resetsAt`, else 15 minutes, at most seven days. A marker with no reset written by a session that started before the account in use was switched to belongs to the previous account and is skipped (`an_old_sessions_marker_without_a_reset_is_not_charged_to_the_new_account`). Errors written in the first 60 seconds after a switch are not held against the new account, as a conservative cache-adoption heuristic; the adoption latency of a running session remains unverified (SB-06). After a restart the journal's latest `activation completed` / `rotation switched` for the account in use dates that switch. A marker carrying the same reset as a hold already charged to another account comes from a session still running on that account and is ignored, and a marker within 10 seconds of a managed 429 is that proxy session's echo (`after_a_restart_the_journal_dates_the_last_switch`, `a_marker_with_another_accounts_reset_is_not_charged_to_the_new_one`, `a_proxy_session_429_is_not_charged_to_the_native_account`). Holds live in memory; markers within the window are read again after a restart. A limited account in use moves at once, inside the cooldown (`limit_reached`, then `switched_on_limit`), to the unlimited eligible account with the lowest fresh usage below 100% — the usual headroom does not apply, since the account in use fails every request; a limited account is never a candidate; with no free account the decision reads `limit_no_eligible_account` (`a_limit_error_switches_despite_spare_quota_and_skips_limited_candidates`, `a_limit_error_in_claude_code_switches_with_quota_to_spare`). `MonitorStatus.limited` lists `{account_id, until, source}`; the row shows *Limit reached*, the separately labelled *Retry hold until {date}* and a countdown (SCN-032). A hold may be estimated; its expiry is not a verified quota reset.

Hold reasons include cooldown, current account unavailable, usage unavailable, below threshold and no eligible account. A failure is shown separately from a successful switch: `activation_failed` for the `claude_cli` target, `switch_failed` for a managed route. An automatic switch records `rotation switched` or `rotation failed` for the candidate; a native one also records its `activation` outcome. If every account is exhausted, stale, disabled or expired, keep the current selection and explain why. A 429 response is not automatically replayed. Only subsequent requests may use a newly selected identity.

```sh
switchboard rotation set --provider claude --target managed --enabled true
switchboard rotation set --provider claude --target claude-cli --enabled true
switchboard rotation status
switchboard rotation set --provider claude --target claude-cli --enabled false
```

An offline policy change is saved but cannot monitor or switch until an owner runs. `rotation status` reports that distinction. Quota, control and metadata errors remain sanitized.

## Activity journal

The store keeps the latest 256 sanitized events. Since 0.5.1 a successful managed request records nothing, so request traffic cannot evict account and selection history (`successful_requests_never_push_other_events_out_of_the_journal`). Every unsuccessful one records one outcome: `request` with `unauthorized` (401/403), `rate_limited` (429, which the limit detector reads), `upstream_error` or `network_error`, or `proxy aborted` when a stream ends early or stays idle past the 600-second read timeout (`every_unsuccessful_outcome_is_still_journaled_once`, `only_unsuccessful_requests_are_journaled_and_usage_is_kept`, `a_stream_idle_past_the_read_timeout_is_cut_and_journaled_as_aborted`). Response-header usage is merged into the stored observation, not journaled. Older files that contain `proxy started`/`completed` or `request success` still open.

## Platform and storage boundaries

macOS current Claude OAuth uses its native Keychain namespace (including custom-home suffix); Windows Claude uses the native credential file. Codex file capture is supported; compatible direct macOS Keychain mode is read where configured. Unsupported keyring/secrets modes report unavailable and offer isolated official login. Environment/config overrides apply to the process running Switchboard; a Finder-launched app cannot infer an arbitrary other shell's transient variables.

Metadata version 2 reads version 1 with defaults and writes new fields atomically. Older binaries must not write version 2. Native context needed for activation is inside the protected credential envelope, not metadata or IPC. Imports never change third-party file permissions. Bounded reads, traversal/reparse checks, identity validation and source drift checks apply before importing.

Synthetic tests cover storage/policy, external adapters and monitor/control integration. Real CLI adoption timing, provider responses and native Windows behavior require the acceptance packet; a cross-build does not establish them. Packaging/signing evidence is recorded per artifact in the release report.

### Quota evidence and waits — 2026-10-04

Aggregate quota age conservatively follows the oldest window retained from partial headers, while latest-check health records the real attempt time. Fresh authoritative JSON can replace historical windows. See [contracts](CONTRACTS.md#quota-evidence-age-and-presentation-2026-10-04) and `partial_headers_never_freshen_an_unobserved_low_quota_window`. Rows preserve provider/pool boundaries and rank fresh remaining capacity before constrained waits and unknown evidence.
